## 2. 必须先修正的问题

### R1：final 金标实际仍在仓库中，盲审包还带标签提示

`scripts/body.py:23` 从 `samples/src-batch*.jsonl` 加载全部样本；这些已提交源文件包含 final 的 `labels` 和 `basis`。中控只用仓库内容重建全部 62 条 final 金标，得到的 SHA256 与 manifest 的 `4b245c18a634322550f537f5be46702f4900c7633c69743debb342ccac5efcbc` **完全一致**。因此“金标没有进仓库”不成立。

另有 16 条盲审记录包含 `ambiguous_by_design=true`，而 LABEL_SPEC §0.3 要求看到该标记就判不确定；该标记不在模型输入中，给盲审者会构成额外答案提示。

修正要求：

- final 推理入口只读取无标签输入；最终评分由独立入口显式读取仓库外的金标文件并核对哈希。把 final 的 labels/basis 从后续提交的源数据中拆出并保留外部副本，绝不为了“消除历史”重写 Git 历史或删除旧封存件。
- 明确旧提交可找回答案的历史事实。给复核者**单独导出的包**：匿名 ID、模型实际可见的文本、统一标签规范、空白答案表；不提供仓库、原标签/依据、模型预测/报告、场景家族/切分或 `ambiguous_by_design`。标签必须由文本证据决定，不能由样本作者的隐藏意图决定。
- 两位复核者相互独立，不看对方结果；已看过原标签、报告或此聊天具体例题的人不得充当对应样本的盲审者。裁定人可在双方提交后看分歧，不由原标注人单独裁定。记录逐信号一致率、κ、类别支持量和分歧，不只给总体 κ。
- 不自动废弃原 62 条：若从未用于调参/看模型最终结果，且新的复核者没有接触其答案，可以匿名复核后保留。受过答案或预测污染的样本降为开发/诊断，并替换新 final。按新版本另存金标与 manifest；旧封存哈希保留历史用途，不强求裁定后的新金标等于旧哈希。

### R2：主指标漏算失败项，macro-F1 的类别集合也不统一

`scripts/score.py:235–243` 先过滤 `predicted is None` 再算准确率/F1。中控运行最小反例“两题，一题正确、一题超时”，得到 accuracy=1.0，按全量计划题目计算应为 0.5。现有 selftest 反而把该过滤结果当作正确行为。本轮存量预测无失败，因此此缺陷没有改变已报告的准确率，但会影响后续异常与超时测试。

此外 `macro_f1()` 跳过金标和预测都未出现的类别；当前 dev/trust_shift 的 A 用 3 类、B 用 4 类求均值，calibration 上相反，横向比较口径不统一。

- 主准确率分母固定为全部计划场景，失败、超时、缺失、非法输出均计为未答对；另列成功返回样本指标、运行成功率及拒答覆盖率，不能混用分母。
- macro-F1 固定使用该信号的同一类别集合，定义零支持类别处理；同时列每类支持量，不能由某模型预测了哪些类决定平均范围。混淆矩阵显式容纳非法/缺失输出，主表与 paired 差值使用相同计划样本。
- 拒绝重复 ID、非法 label、NaN/Infinity 或不合法概率，保留原始错误；测试“两题一超时”“全失败”“固定类别中一类无支持”“A/B 同题不同失败”“重复预测”。修后重算存量结果，保留原始预测不覆盖。
- 当前 majority 是从被评估集金标事后挑出的最优常量，应标为 oracle-majority 描述基线。正式可部署多数类基线应从开发集确定，再锁定到 calibration/final；两者分别报告。

### R3：禁止 final 参与校准，冻结不能只看一个布尔值

M4 报告 §2(4) 写“在冻结后的最终集上重拟”；`score.py` 只拒绝同切分拟合，中控最小反例 `--split dev --calibrate-from final` 成功执行。正式流程必须是开发集选择方法、校准集拟合参数/阈值、最终集只评分。

- 删除 final 拟合入口；正式输出固定 calibration 拟合，写出模型/信号对应的校准参数与哈希，final 只加载该成品。现有 dev↔calibration 交叉试验保留为 pilot 诊断，不能写成最终验证。
- final 开跑前校验独立复核与裁定回执、样本及问题模板哈希、实际模型/配置版本、冻结的校准与阈值记录；缺失、变更或尚未冻结都应拒绝，不能只设置 `final_frozen=true` 就通过，也不能用 `--allow-unfrozen` 绕过正式 final。
- 测试 final 作为拟合集必拒绝、模板/样本/参数哈希改动必拒绝、旧封存记录不被构建脚本覆盖。重跑验证器不能清掉冻结信息后静默继续。

### R4：稳定性条件要实际改变输入，截断与超时要有真实实现

`run_bench.py:37,109` 的 primary/long/paraphrase 都调用相同 `build_body(r)`；`max_len_8192` 的名称也不会自动改变默认长度。文档中的截断政策没有被执行。`body.paraphrase()` 的机械替换“你→阁”等不能证明语义不变。异常捕获也不等于设置并执行超时。

- 先用 dev 测试真实的置换、人工复核的等义改写、短/长上下文和空/异常输入；记录最终传入的文本/选项/token 数、删除了哪些证据及配置。长文本截断若删掉了判断依据，按新的可见文本重新审标签或单列，不拿原金标硬算。
- 置换按稳定语义 ID 映射，测试映射回原标签无误；对照输入须可检查且确有差异。新增有界超时及错误记录，禁止异常条件落回 primary 却保留条件名。
- 四类稳定性条件先在 dev 完成实现和诊断，calibration 只用于已确定方案的校准/检查；出现新的调参行为就把受影响批次归为开发数据并补新的校准批次。最终集在冻结后按预先确定的主测/压力子集方案一次评估，不留到 final 才调试条件。

### R5：标签定义、复现与报告措辞

- 先澄清“有欺骗线索”与明显反讽/虚构/不可核实陈述的区别，不能默认反讽就是欺骗；分开“NPC 自己知道边界”与“玩家是否已被告知”。不确定应来自可见信息不足，不能由隐藏 metadata 强制。
- 改正报告里的过度推断：未观察到正确的不确定分类，不等于证明没有任何拒答途径；相同 tokenizer 不证明 C 或未来微调同样失败；配置改写而权重相同不证明预测不变，需要实际 token/输出对照才能下结论。
- 确定性 fallback 只处理结构化、已知、可核验的事件/规则；无法从自由文本可靠提取事实时返回未知/不改变状态，不能把“规则判断”写成已解决自由文本欺骗检测。
- 修正复跑命令中 `.. \venv\...` 的无效路径，按 lock 文件锁定环境依赖；原始下载目录保留只读来源证据，用单独运行副本容纳 SDK 改写，记录运行时实际配置/哈希。不得宣称仅加载前哈希即可证明运行时配置一致。
- 清理本任务误提交的两个 `scripts/__pycache__/*.pyc` 并添加局部忽略；只处理精确的本任务产物，不动模型文件或其他项目。
